## 目标与已确认范围

将参考 Android 应用在指定提交中的页面和功能迁移到当前 Flutter 工程，Android 与 iOS 共用页面、控制状态、设置、布局编辑和通信协议。用户已明确允许读取、修改 `lib`。不读取、修改 `linux`、`web`，不改动 `stm32` 固件。

参考版本固定为：

https://github.com/Norlive666/remote-control/tree/76dc101fc07e57cbd3b6195a8d34f80ccce2b71d/android

依据文件：`MainActivity.kt`、`EditablePanel.kt`、`RemoteViewModel.kt`、`BluetoothTransport.kt`、`ControlProtocol.kt`、`JoystickConfig.kt`、`SliderConfig.kt`、`SliderSettings.kt`、`PanelLayout.kt`，以及现有协议测试和 UI 测试。

当前工程的 `lib/main.dart`、Android Activity、iOS AppDelegate / SceneDelegate 均为 Flutter 模板。目录不是 Git 仓库，因此方案和后续改动直接保存在当前工作区，不创建提交。

`stm32/f103` 与 `stm32/h723` 对应两款 MCU；它们的协议处理 C 文件完全相同，头文件分别选择 F1 / H7 HAL。文件包含默认 9600 波特率初始化和 BT630 的 115200 波特率初始化。手机应用控制 BLE GATT，UART 波特率由模块与 MCU 侧配置。

## 技术方案

采用 Flutter 页面与纯 Dart 业务模块，使用 Flutter 平台通道连接 Kotlin Android 蓝牙实现、Swift iOS CoreBluetooth 实现。

这延续当前工程结构，统一两端的页面和行为，也能保留参考 Android 的 BLE 与系统发现合并逻辑。另一种可行方案是第三方 Flutter BLE 插件；它能减少原生代码，但系统发现及诊断需要另外补齐，还需评估插件兼容性和许可。本方案选择原生蓝牙桥接。

模块职责：

- 协议模块：控制状态、帧编码、CRC、序号处理，不依赖 Flutter UI 或蓝牙。
- 配置模块：摇杆映射、滑块映射、布局归一化坐标、缩放和草稿事务。
- 控制器：连接状态机、前后台处理、发送循环、诊断状态、设置持久化。
- 页面：主操控面板、蓝牙弹窗、设置弹窗、布局编辑栏、双摇杆指针处理。
- 平台桥接：蓝牙权限、扫描、连接、服务发现、通知接收、串行写入、关闭，以及本地设置读写。

平台使用系统蓝牙 API。设置用 Android SharedPreferences / iOS UserDefaults 保存带版本的 JSON。通过 MethodChannel 提交请求，通过 EventChannel 发布设备、连接、扫描和接收事件。接口必须有明确的错误码和连接代次，忽略已取消连接的迟到回调。

iOS 不显示 Android MAC 地址，显示设备名称与 CoreBluetooth 标识；不复制 Android 系统发现、定位权限提示。两端均实现参考的两种 BLE 模式，不增加经典蓝牙 SPP。

## 通信协议与状态约束

| 字节 | 内容 |
| --- | --- |
| 0～1 | `A5 5A` 帧头 |
| 2 | 版本 `01` |
| 3 | 8 位序号，按模 256 增长 |
| 4～11 | LX、LY、RX、RY，四个有符号 int16，小端，范围 -1000～1000 |
| 12～15 | 两个 uint16 滑块，小端，范围 0～1000 |
| 16 | bit0：使能；bit1：stopped；其余位为 0 |
| 17 | 保留字节 `00` |
| 18～19 | CRC16-CCITT-FALSE，小端；初值 FFFF，多项式 1021，覆盖字节 2～17 |

禁用或 stopped 时全部轴和滑块编码为零，stopped 不与使能同时有效。帧长固定 20 字节，可在默认 BLE MTU 下单次传输。

MCU 300ms 未收到有效帧会归零、关闭使能并清除链路有效标志；超时恢复要求先接收禁用帧。连接完成后必须先提交禁用帧，提交成功之前不开放使能。每次断连、模式切换、退后台均清除轴和滑块并关闭使能，重新连接需要用户手动使能。

每条连接仅保留一个进行中的写入，不累积旧摇杆帧；下一次发送采样最新控制状态。优先选择 writeWithoutResponse，否则使用 writeWithResponse。发送频率是目标上限，受实际链路速度影响，不声称写入完成就是固件已收到。

关闭使能后下一帧必须为最新零输出。主动断开或退后台时，在平台仍允许且链路可用的情况下尝试发送禁用帧，随后停止发送并关闭连接；无法传输时依赖现有 MCU 300ms 看门狗。不得为了等待写入而阻塞 UI。写入错误、连接超时或蓝牙关闭应立即清除本地使能并呈现可理解的错误。

BLE 连接请求使用约 10 秒平台超时，并提供 12 秒上层截止保护；单次写入最多等待 1 秒，期间 MCU 看门狗仍独立生效。检测到发送完成间隔达到 300ms 时，清除使能，恢复发送先发禁用帧，防止超时后继续自动恢复运动。

通知只显示原始数据。现有固件没有 ACK 协议，不能把任意通知当作控制确认。

## 平台配置与错误处理

Android：声明蓝牙扫描 / 连接权限以及参考扫描需要的定位权限；按系统版本申请运行时权限。保留参考的定位开关检查和 BLE + 系统发现诊断，权限拒绝支持再次申请或进入应用设置。检查蓝牙开关、服务 UUID、特征写入属性，串行处理 GATT 操作；扫描与广播接收器随连接、弹窗关闭和生命周期正确释放。

iOS：补充蓝牙使用说明，按 CoreBluetooth 状态区分未授权、蓝牙关闭、不支持和就绪；扫描、连接、发现服务 / 特征、订阅通知与发送均通过指定队列。writeWithoutResponse 使用系统可写状态做流量控制；writeWithResponse 等待完成回调。应用退后台停止控制，本方案不申请后台持续遥控能力。

每次扫描、连接、断开都会更新代次；迟到回调不得恢复旧设备、旧连接或旧使能状态。写入与连接错误通过稳定错误码通知 Dart，UI 显示中文处理建议。设置保存失败须保留当前可恢复状态并报告错误。

## 验证与交付标准

1. 协议测试：标准 CRC 向量 `123456789 → 29B1`；参考的 20 字节固定向量；负数小端、边界钳位、禁用 / stopped 清零、序号回绕。可用主机 C 工具链时，将 Dart 输出喂入两套 `RC_HOST_TEST` 固件解析器，覆盖禁用首帧、300ms 超时、恢复和重复 / 旧序号拒绝。
2. 映射与状态测试：各摇杆模式、死区、四向平局、实际滑块档值；断连 / 后台清零；恢复需手动使能；发送无旧帧堆积；迟到回调无效。
3. UI 测试：参考三栏结构和文案、多点双摇杆释放与取消、模式切换中止旧手势、设置输入验证、七元素编辑 / 缩放 / 边界 / 保存 / 取消、重启恢复、小屏横竖屏无布局溢出。
4. 本机运行 Flutter 静态分析与测试。发现 SDK / 工具限制须记录实际错误，不以未运行检查宣称通过。
5. 用户后续明确要求构建与打包另行安排；本阶段完成 Android 源码和配置检查，不执行 debug / release 打包。当前未发现 Android SDK、Kotlin 编译器和 JDK17。
6. Windows 无法运行 Xcode / iOS 构建。交付 iOS 源码、工程配置与后续 macOS 检查步骤；云端构建、签名和 IPA 导出按用户要求后续安排。
7. 硬件验收分别连接 FFE0/FFE1 和 BT630；验证连续控制、双指、20/50Hz 目标、关闭使能、切换模式、断开、退后台及 300ms 超时恢复。当前未提供已连接手机与模块，实机结果不得被模拟测试替代。

后续实现按协议与配置 → 原生蓝牙桥接 → 控制器 → 页面 / 编辑设置 → 验证的顺序推进。方案确认后生成逐项实施计划，再开始产品代码开发。
